## 可操作的验收步骤

建议在新建的验收项目内执行，避免删除真实历史。管理入口保持 `http://localhost:8080`。

1. 上传一个 HTML 或 ZIP，待可预览后进入版本工作空间，点击“下载原型原件”。将下载文件与上传文件执行 `shasum -a 256`，两者应相同；ZIP 下载应为原包。
2. 上传第二个版本，再上传第三个版本时指定 v1 为基线。时间线和工作空间应显示并链接 v1；默认值应选择最近成功版本，失败版本不在可选列表。明确选“无”时应显示“无”。已有历史版本应显示“未记录”。
3. 将当前预览或发布指针指向较早的成功版本，删除未被指针引用的最高版本，再上传。新编号应继续递增；不能重新使用刚删除的编号。
4. 在 v2 备注或正文放入独有关键词，再上传不含该词的 v3。首页搜索应显示“版本内容命中 · v2”，点击进入 v2；搜索资产名的“资产信息命中”仍进入资产详情。
5. 用可通过上传校验、但预览入口缺失的 ZIP 触发预览失败。页面应显示“原件已保存 · 预览失败”，仍能下载原包。上传被拒绝时不能显示已保存成功。
6. 未登录请求原件下载应返回 401，其他用户请求应返回 404；原件确实缺失时返回 404，对象存储暂不可用时返回 503。
7. 确认项目和版本页显示“当前发布原型”相关文案，材料区明确说明设置发布原型不会固定资料。

1. 停止 Caddy、API 和 Worker 的写入，保留当前数据库及对象存储的额外备份，尤其是迁移后已上传的新内容。
2. 优先修复或回退应用代码，保留本次新增列；不要直接删除列或降低计数。保留镜像标签为 `prototype-hub-phase1-rollback-{api,web,worker}:20260907`。旧版 API 不具备新编号语义，回退验证期间保持入口和 Worker 停止，不恢复写入。
3. 若必须恢复到备份时点，先在全新 PostgreSQL 数据库运行 `pg_restore --exit-on-error -U prototype -d prototype_hub` 导入 `database.dump`；将 `minio-data.tar.gz` 解压至新的空 MinIO 数据卷，再启动 MinIO。不要覆盖正在运行的数据库或 MinIO 卷。
4. 为恢复环境配置匹配的数据库、S3 地址、bucket 及凭据。核对全部表记录、父子关系、预览/发布指针、对象清单、7 份原件的大小与 SHA-256，并验证下载与预览。仅检查 `pg_restore` 的退出码不算完整恢复验证。
5. 验证通过后再切换应用至恢复的数据卷和匹配镜像。完整恢复会回到备份时间点，迁移后的新增数据须先另行保存。不要使用 `docker compose down -v` 清理正式卷。
